## 一、系统概述

### 1.1 系统定位
我们正在构建一个 **AI 视频生成预生产系统**（对标 "视频生成行业的 cloud code"），目标是让高质量短片创作触手可及。系统基于 **Seedance 2.0 API**（字节跳动火山引擎视频生成服务）进行视频渲染。

### 1.2 三系统架构
```
卓越主系统 (systems/ + zhuoyue-system/)
├── 核心预生产链路（16-20 Stage）
├── 角色系统、运镜系统、光影系统
├── 质量门检查、导演优化
└── 当前版本: v6.6.5

超短裙系统 (short-video-system/)
├── 15秒短视频专用链路
├── 字符数上限1500（vs 卓越系统490）
├── 产品展示、营销视频
└── 当前版本: v0.7.3

超现实系统 (hyperreality-system/)
├── 超写实/超现实风格
├── 金色光影软性注入
├── 氛围系统
└── 当前版本: v1.2.0-alpha1
```

### 1.3 核心工作流（16-20 Stage）
```
Stage -1: 需求解析 → 输出需求清单（v6.6.0新增）
Stage 0: PRD中央校准
Stage 1: 需求对齐闸机
Stage 2: Schema校验
Stage 3: 角色系统 (CharacterManagerV2 + CharacterPromptBuilder)
Stage 4: 剧本生成 (LLM驱动，批次处理)
Stage 5: 视觉Prompt生成

Stage 13-16: 输出交付
```

## 二、当前版本问题汇总（v6.6.5）

### 🔴 问题1：需求清单确认流程未正确触发（v6.6.4新增功能失效）

**现象描述**：
- v6.6.4 新增了【视频需求清单确认流程】，要求预生产开始前必须完成需求清单确认
- 用户反馈："你会给我一个'视频需求要点清单'，让我确认，但是你貌似没有给我过"
- 实际运行中，系统**没有输出需求清单**给用户确认，而是直接进入了预生产链路

**根因分析**：
1. `user-requirement-parser.js` 的 `generateRequirementList()` 方法已存在，但可能未被正确调用
2. `nirath-master-pipeline.js` 的 Stage -1 逻辑可能存在判断条件错误
3. `skipRequirementConfirmation` 默认值可能为 `true`，导致跳过了确认环节
4. 清单输出路径可能指向日志文件而非用户可见的输出

**相关代码**（`systems/user-requirement-parser.js`）:
```javascript
generateRequirementList(parsed) {
  const sections = [];
  sections.push('# 视频需求要点清单');
  sections.push('');
  sections.push('## 1. 视频任务基本信息');
  sections.push(`- 视频类型：${parsed.videoType?.value || '未指定'} (置信度: ${parsed.videoType?.confidence || 'N/A'})`);
  // ... 更多字段
  return sections.join('\n');
}
```

**相关代码**（`systems/nirath-master-pipeline.js` Stage -1）:
```javascript
async stageRequirementParse(input) {
  const parser = this.modules.userRequirementParser;
  const parsed = await parser.parse(input);
  
  // 生成需求清单
  const requirementList = parser.generateRequirementList(parsed);
  
  // 保存到文件
  const listPath = path.join(this.outputDir, `requirement-list-${Date.now()}.md`);
  fs.writeFileSync(listPath, requirementList);
  
  // 检查是否需要确认
  if (!input.skipRequirementConfirmation) {
    return {
      status: 'REQUIREMENT_CONFIRMATION_REQUIRED',
      requirementList: requirementList,
      listPath: listPath,
      parsed: parsed
    };
  }
  
  return parsed;
}
```

**问题点**：
- 清单保存到 `output/requirement-lists/` 目录，但用户未收到通知
- 返回状态 `REQUIREMENT_CONFIRMATION_REQUIRED` 后，调用方可能未正确处理该状态
- 用户确认机制依赖手动再次调用，无自动化中断-恢复能力

**期望结果**：
- 用户输入任务后，系统**立即输出**需求清单给用户
- 用户回复"确认"后，系统才进入预生产链路
- 用户提出修改时，系统迭代清单（最多1-2轮）
- 最终版清单锁定后进入下游

**违反后果**：按SOUL.md规定，未确认需求清单启动预生产 = **系统级错误**

### 🔴 问题2：LLM content为空 + JSON解析失败（Stage 5 剧本生成）

**现象描述**：
- Stage 5（LLM剧本生成）批次执行时，`content` 字段为空
- `reasoning_content` 有6208字符，但全部用于思考过程，无有效JSON输出
- JSON解析失败：`Expected property name or '}' in JSON`

**日志示例**（v6.5.26，问题仍存在）：
```
[LLMEngine] ✅ API 推理完成 | Tokens: 3000
[LLMEngine] 📥 输出长度: 2000 字符
[STAGE-5] ⚠️ 批次 1 失败: JSON parse error: Expected property name or '}' in JSON
[MEM] 批次 1 后 | heapUsed=15.2MB | rss=85.5MB
```

**根因分析**：
1. `maxTokens=3000` 设置过小，LLM（kimi-k2p6）将全部tokens用于推理过程，无剩余token输出content
2. reasoning_content 是思维过程文本，不是JSON格式，从其中提取最后2000字符无法解析为JSON
3. 健康科普场景的prompt较长（1300-1550字符），导致LLM需要更多token思考

**相关代码**（`systems/nirath-master-pipeline.js`）:
```javascript
async _llmGenerateScript(input, prd) {
  const { LLMEngine } = require('./llm-reasoning-engine');
  const llm = new LLMEngine({ 
    model: 'kimi-k2p6', 
    mode: 'production', 
    maxRetries: 2, 
    maxTokens: 3000  // ← 问题：3000太小
  });
  // ...
}
```

**相关代码**（`systems/llm-reasoning-engine.js`）:
```javascript
async reason(prompt, options = {}) {
  const response = await fetch(url, { ... });
  const result = await response.json();
  
  const content = result.choices?.[0]?.message?.content || '';
  const reasoningContent = result.choices?.[0]?.message?.reasoning_content || '';
  
  let finalContent = content;
  if (!finalContent || finalContent.trim().length === 0) {
    if (reasoningContent && reasoningContent.trim().length > 0) {
      // v6.5.22-fix: 从reasoning_content提取最后2000字符
      finalContent = reasoningContent.slice(-2000);  // ← 问题：不是JSON
    }
  }
  
  return { content: finalContent, ... };
}
```

**期望结果**：
- LLM 输出有效的JSON格式内容，包含 `scenes` 数组
- 每个场景有 `dialogue`, `narration`, `visualPrompt`, `mouthAction`, `emotionPhase` 字段
- JSON解析成功率100%

### 🔴 问题3：进程被SIGTERM终止（非OOM）

**现象描述**：
- 运行预生产时，进程被 `SIGTERM` 信号终止，不是OOM
- 内存监控显示 heapUsed=15.2MB（正常），rss=85.5MB（正常）
- 进程仅运行2分37秒，未达到超时阈值（600秒）

**日志**：
```
... Process exited with signal SIGTERM
```

**可能原因**：
1. 系统cgroup限制（Docker容器内存限制）
2. 系统定时任务（cron job）发送信号
3. OpenClaw exec超时（但设置600秒，进程仅运行2分37秒）
4. 系统资源限制（如systemd的TimeoutStartSec）
5. 其他进程发送信号

**期望结果**：
- 预生产过程稳定完成，不被SIGTERM中断
- 明确SIGTERM来源，建立防护机制

### 🔴 问题5：环境布景Nirath科幻残留（generic模式）

**现象描述**：
generic 模式的 prompt 中出现了 Nirath 科幻描述：
```
【环境布景】中景原始发光毯覆盖地表，随磁场脉动明暗。
生态活跃：原始单细胞发光毯覆盖地表；矿物结晶生长过程缓慢可见。
禁止塑料/CG质感，禁止光秃秃/荒芜/寸草不生

**问题**：
- "发光毯覆盖地表"、"磁场脉动"、"矿物结晶" 是 Nirath 外星场景特征

- 尽管已有多处 `if (this.mode !== 'nirath')` 守卫，但环境布景仍有渗漏

**相关代码** (`systems/nirath-master-pipeline.js` line ~4481):
环境布景的注入逻辑可能未被 mode 守卫覆盖。

**期望结果**：
```

### 🔴 问题6：质量评分仍低（34-62 / 目标 90+）

**现象描述**：
即使经过多次修复，质量分仍然很低：
```json
S01: 34分
S02: 34分  
S03: 36分
S04: 34分
S05: 34分
```

**v6.6.4修复后预期**：53-62分 → 75-85分（仍未达到90+）

**质量分维度**:
```json
{
  "cameraVariety": 0,        // 运镜多样性
  "lightingProgression": 8,  // 光影递进
  "emotionalDepth": 7-9,   // 情绪深度
  "promptUtilization": 15, // Prompt利用率
  "narrativeAlignment": 4,  // 叙事对齐
  "totalScore": 34-36,
  "segmentCount": 0
}
```

**问题分析**：
- `cameraVariety: 0` — 所有镜头都是 `static shot`，没有变化
- `promptUtilization: 15` — 远低于 490/1500 字符上限（利用率可能只有 15%）
- `narrativeAlignment: 4` — 与叙事对齐度极低
- `segmentCount: 0` — 没有分段

**可能原因**：
1. 质量评分算法本身可能有 bug（比如 `segmentCount` 为 0 但 prompt 实际有内容）
2. Prompt 结构问题（大量重复内容，如角色描述重复 3 次）
3. 缺少动态运镜（全部 static）
4. 评分算法与generic模式不匹配（算法针对Nirath模式优化）

**期望结果**: 质量分达到 90+（A级），或至少明确质量分算法是否合理

## 五、期望结果总结

我们需要系统达到以下状态：

1. **需求清单正确输出**：用户输入后，系统立即输出完整的需求清单，等待用户确认
2. **LLM输出稳定**：content不为空，JSON解析成功率100%，不被SIGTERM终止
3. **角色差异化**：每个角色有符合身份的年龄、性别、服装、外观描述
4. **角色约束正确**：显示所有在场角色，不硬编码单一角色
5. **环境真实**：generic 模式完全清除 Nirath 科幻元素，使用真实场景描述
6. **质量分达标**：90+ 分（A级），或至少明确质量分算法是否合理
7. **系统健壮**：避免 `[object Object]`、类型错误、字段遗漏等回归缺陷
